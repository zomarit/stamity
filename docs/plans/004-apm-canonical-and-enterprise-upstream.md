# The 1.4.0 release — APM served from the main repository, and the enterprise upstream lane

## Context

Two coordinated changes for the next release, decided by the maintainer on 2026-09-09 as one
overnight autonomous run (the four answers below), landing as one reviewable pull request and
then the 1.4.0 cut by the repository's own release process.

**One.** The APM package (`apm.yml` + `.apm/`, generated by `scripts/generate-apm-package.mjs`)
has been a correct but unreachable surface since 1.0.1: APM's type-detection cascade routed a
tree carrying a root `plugin.json` away from it, so a mirror repository (`zomarit/stamity-apm`,
created 2026-08-31, a six-hourly self-sync from the latest tag) served the package instead. APM
fixed the cascade (microsoft/apm#2735 → PR #2776, merged 2026-09-03, shipped in 0.29.1 on
2026-09-06). The main repository is now the canonical APM source as it stands; the change here
proves it, gates it, documents it, and retires the mirror.

**Two.** An organisation that forks this repository, customises anything in it, and wants the
next upstream release with its work intact has had no supported path. The enterprise upstream
lane (`docs/specs/enterprise-upstream-lane.md`) is that path: one plain-Node script, one opt-in
workflow, one config file, an acceptance suite over temporary repositories.

**Decisions, each with the reading taken and the reading dropped**, in the question protocol's
words. The maintainer answered four questions before the run started (2026-09-09, ~23:35 local):

- *Landing scope — answered:* full 1.4.0 release tonight: merge on green, the per-release full
  eval run (run 10), the cut, the tag, the publish approval as the maintainer's delegate, the
  currency rows, then the mirror's backup and deletion. Dropped: PR-only, and merge-without-release.
- *Deletion — answered:* grant the `delete_repo` scope (a browser refresh the maintainer runs in
  the session); the recovery backup lives in the private governance checkout under
  `archives/stamity-apm/` plus a local copy. Dropped: local-only backup; no deletion tonight. If
  the scope is not present when the cutover is reached, every preparatory step completes and the
  one-line delete command is handed over — no archive-instead-of-delete substitution.
- *Fixture repository — answered:* a temporary private repository under the organisation, a plain
  clone with history (not a fork-network member), runs the upstream workflow twice for real and is
  deleted afterwards. Dropped: local-only evidence for the Actions layer.
- *Process — answered:* direct engineering with sub-agent fan-out and the repository's record
  artifacts (this plan, the run record, the ledger); the QA sign-off row stays the maintainer's.
  Dropped: the `/st-plan` → `/st-work` touchpoints with their deferred human checkpoint.
- *Assumption taken:* the next version is 1.4.0 — a semver minor: both changes add capability
  (an advertised install route and a new lane) and nothing shipped changes shape. Dropped: 2.0.0
  (no breaking change exists; the minimum APM client is a documented requirement of a new route,
  not a change to an old one) and 1.3.1 (a patch may not add behaviour).
- *Assumption taken:* the lane is a `scripts/*.mjs` tool, not a CLI verb — it must run in a
  tree that is mid-merge and may not build. Dropped: `stamity upstream` in `dist/cli.js`.
- *Assumption taken:* no edit under `content/` in this change, so no prompt-triggered eval slice
  opens; the release runs the full set by the standing rule. Dropped: a new `st-upstream` skill.
- *Assumption taken:* the eval run and the acceptance evidence use the workflow harness of record
  (explicit model ids), which the maintainer's "full release" answer sized at ~207 scenario agents
  and ~207 judge calls. Dropped: tier-alias dispatch through the agent tool, which the set forbids.
- *Assumption taken:* an "org overlay" content layer inside the fork's package is the natural next
  step and is NOT built tonight; it touches the catalog's precedence chain and the corpus-count
  pins and gets its own spec. Recorded in the lane spec's non-goals with its trigger.

### APM (research note: `scratchpad/research-apm/apm-research.md`, 669 lines; probes: `evidence/apm-probes-2026-09-09.md`)

- Issue: https://github.com/microsoft/apm/issues/2735 (opened 2026-08-31, closed 2026-09-03). Fix:
  https://github.com/microsoft/apm/pull/2776 (merged 2026-09-03T23:12:58Z, merge commit
  `7baf88292f4ec11152e1642d61ee3dcd86d36b66`). `git tag --contains` → `v0.29.1`, `v0.30.0`.
  Release notes v0.29.1 (published 2026-09-06T07:47:16Z) carry the PR; v0.30.0 (2026-09-07)
  inherits it. PyPI wheels: 0.29.1 at 2026-09-06T07:47:59Z, 0.30.0 at 2026-09-07T09:54:17Z.
- The rule (`src/apm_cli/models/format_detection.py:451-460@v0.30.0`): an `apm.yml` is *eligible*
  when `.apm/` exists OR the manifest declares an APM/MCP dependency; an eligible manifest wins
  over root `plugin.json` (any schema) and `.claude-plugin/`. A metadata-only manifest still lets
  plugin signals win. The detection code is byte-identical at v0.29.1, v0.30.0 and `main`
  (2026-09-09); no regression reported; #2831 confirmed the fix on the released 0.29.1.
- No manifest key can declare a minimum APM client version (grep of `src/`, `docs/`, the JSON
  schema at v0.30.0). The minimum is therefore a documented requirement plus the exact symptom
  string an older client prints.
- Remote installs `git clone` (shallow for tag/branch, full for sha) and strip `.git`; no
  `export-ignore`, no `.apmignore`. Everything committed at the ref is vendored under
  `apm_modules/` — 870 files, 19 MB for this repository versus 54 files, 476 KB from the mirror;
  the deployed primitives are byte-identical (`diff -r` of the two `.claude/` trees).
- `apm install` has no `--json`; `apm.lock.yaml` is the machine-readable record
  (`package_type`, `resolved_commit`, `deployed_files`, `deployed_file_hashes`).
- Executable evidence (2026-09-09, three venvs): 0.29.0 reproduces the original failure on both
  routes (exit 0, zero primitives; the declarative copilot form "registers" the plugin and deploys
  nothing); 0.29.1 and 0.30.0 deploy 10 agents, 9 commands, 12 rules, 8 skills from
  `zomarit/stamity` (main) and `zomarit/stamity#v1.3.0` for claude, copilot, cursor, codex (codex
  takes agents and skills; APM's codex profile carries no commands and compiles instructions on
  `apm compile`). The imperative local-path route is still refused for a tree with a root
  `plugin.json`; the declarative local form (a consumer `apm.yml` naming the path) deploys all 49.
- Follow-up worth watching: microsoft/apm#2806 (merged 2026-09-09, unreleased) makes an Agent
  Plugin that deploys to no target exit non-zero — the class of silent no-op the original failure
  belonged to; it does not touch the precedence rule.

### Enterprise forks (research note: `fork-research.md`, 657 lines, with a reproducible git experiment log; read 2026-09-09)

- **A private copy of a public repository cannot be a GitHub fork**: a fork's visibility is tied
  to its network (github/docs `content/pull-requests/reference/forks.md`, line 59). The private
  case is the documented mirror clone plus mirror push, with no fork features: no Sync fork, no
  merge-upstream endpoint, no pull requests to upstream, and `gh repo sync` fails with "repository
  is not fork". The lane is therefore git-native and needs nothing from the fork network.
- **Upstream `release` and `push` events never reach another repository** (workflow triggers are
  "events that occur in your workflow's repository"); detection is a `schedule` poll or a
  dispatch. Scheduled workflows are disabled by default in a fork and auto-disabled after sixty
  idle days in a public repository (github/docs `data/reusables/actions/scheduled-workflows-disabled.md`).
- **`gh repo sync` is fast-forward-only** (`git merge --ff-only`; source `pkg/cmd/repo/sync/git.go`),
  errors on divergence, and `--force` is `git reset --hard`; it never creates a merge commit
  locally. The web "Sync fork" (the merge-upstream endpoint) does create a merge commit when it
  cannot fast-forward and returns 409 on conflict.
- **Squash and rebase landing both destroy ancestry** — verified on git 2.52.0: after either, the
  release commit is not an ancestor, `rev-list --count` still reports it pending, and the next
  merge re-conflicts on lines only the fork touched, because the merge base regressed to the root.
  The rescue when policy forbids merge commits: the recorded upstream commit as
  `git merge-tree --write-tree --merge-base=<sha>` (git 2.40+) plus `git commit-tree` with both
  parents, or a ruleset bypass for the lane's identity.
- **Token limits on GitHub Actions**: since 2026-06-11 a pull request created with the repository
  token starts `pull_request` runs in an approval-required state (before: no runs at all);
  `gh pr create` with that token needs "Allow GitHub Actions to create and approve pull requests";
  and that token cannot push a commit touching `.github/workflows/` — corroborated by the `gh`
  source's own error text and the peter-evans guidance, with no single docs sentence located. A
  fine-grained token or App token with Contents, Pull requests and Workflows write lifts all three.
- **Reading a landing policy**: `GET /repos/{owner}/{repo}/rules/branches/{branch}` returns
  `required_linear_history` and `pull_request.parameters.allowed_merge_methods`;
  `gh pr merge --merge` under a squash-only policy fails at the API (405 / GraphQL error).
- **No existing tool fits**: wei/pull is a hosted app bound to the fork network that defaults to a
  hard reset; actions-template-sync resolves conflicts with `-X theirs` and squashes;
  repo-sync/pull-request is archived; git-upstream is unmaintained since 2020; git-imerge is
  interactive; Copybara is one-way and Bazel-built; the fork-sync actions auto-merge or push
  directly and need the network. The right primitives are git plumbing (`merge --no-ff --no-commit`
  in a worktree, `merge-tree --write-tree`, `rerere`, `bundle`, `rev-list`, `--diff-filter=U`) plus
  `gh pr create`, which is what the lane uses.
- **Patterns from elsewhere**: Electron and Debian carry downstream edits as an explicit patch
  series; Nix overlays and Kustomize express customisation as a function or a structured patch
  over an untouched base; spec-kit and BMAD keep an install manifest of hashes and refuse to
  overwrite a locally modified managed file. This product's `.stamity/overrides/` and
  `.customize.*` are the same family at the consumer level; the lane carries the residue.

### This repository (the codebase census, 2026-09-09)

- `.apm/` is written only by the generator, never by `sync`; `sync` rewrites 58 ledgered paths
  (`.claude/**`, `AGENTS.md`, `CLAUDE.md`, `.stamity/generated/**`).
- The `main` ruleset requires linear history and allows squash and rebase only — the exact
  landing policy that would lose upstream ancestry in a fork that copies it.
- Adding one hand-written guide moves nine literals (`test/docsPages.test.ts` path-order block,
  `GUIDES`, `HAND_PAGES` contract, `README_LINK_TARGETS`, `website/sidebars.ts`, the llms index,
  the README map row, the docs roster) and the hand-page contract forbids absolute URLs outside
  this repository, bare domains, and emails.
- The gates ladder in `release.yml` is pinned by name; `ci.yml` carries no harden-runner, so a
  PyPI install needs no allowlist there; `release.yml` does.
- The release cut of record is `release-cut.sh` in the private layer plus two hand steps (the
  migration page's banner form; the docs suite's cut-date pin), then the changelog footer moves.
