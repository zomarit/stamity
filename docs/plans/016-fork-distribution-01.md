# Fork and distribution polish — file 1 of 3: fork correctness and the round trip

This file is self-contained. It is the first of three `/st-plan` artifacts for **Package 20**, which makes stamity's
public and private fork support and its three distribution routes — the CLI, APM and the client plugins — work end to
end for any organization. Each file is one session and one pull request. This file merges without a release; file 2
(`docs/plans/016-fork-distribution-02.md`) builds the routes, and file 3 (`docs/plans/016-fork-distribution-03.md`)
writes the docs, proves every route and cuts 1.12.0.

intent chosen: feature because the request names net-new capability (a fork CI job, `fork-identity.mjs --suffix`,
`clean --purge`, the `copilot.setupSteps` key) and asks for the distribution routes to be "polished and state of the
art"; the fork defects ride as units, each opening with the test that fails today, and no dependency moves, so the
migration intent does not fire.

## Context

An enterprise re-set up its private fork on upstream 1.10.0, released it as `1.10.0-<suffix>.2` and rolled it out
through its own orchestrator on 2026-09-29 and 30, then sent a short feedback list and a 67-item brief. On 2026-10-01
this planning run applied the fork identity to 1.11.0 with a suffixed version and a documented
`stamity.distribution.sources` value, and ran the whole gate: 8 tests in 6 files fail only because the tree is a fork.
The fork release's `npm publish` fails on every suffixed version, because npm 11 refuses a prerelease without `--tag`
(`npm error You must specify a tag using --tag when publishing a prerelease version.`, npm 11.21.0, dry run), and the
workflow test stubs npm, so it pins the defect in. The released 1.11.0 CLI, measured in throwaway repositories, does not
round trip: `clean` leaves four `.gitignore` lines and a `settings.json.bak`, `clean -y` deletes every user file under
`.stamity/`, `init --force` doubles the charter, the CLI writes into a folder APM deployed, and the generated Copilot
setup workflow can be neither opted out of nor SHA-pinned.

This file fixes what breaks a fork or a round trip, and adds the guard that would have caught the fork defects: a
canonical CI job that runs the whole gate as a suffixed fork on every pull request. **Out of scope:** the routes' new
capabilities (file 2), the docs pages, the route proofs and the release (file 3), and the drop list.

#### REQ-PLUGIN-031 A fork release publishes its suffixed version under an explicit npm dist-tag (ADDED)

Added `<date>` (plan 016 file 1, unit `u1-npm-dist-tag`). A fork's version carries a prerelease suffix, as the fork guide
recommends (`1.12.0-acme.1`). npm 11 refuses to publish a prerelease version without `--tag`. So
`.github/workflows/fork-release.yml` publishes with `--tag "$DIST_TAG"`. `DIST_TAG` is the repository variable
`STAMITY_RELEASE_DIST_TAG` when it is set, and `latest` otherwise, because the update notice reads `latest`. The
`dry-run-summary` rehearsal runs the same npm check with npm 11 (`npm publish <tarball> --dry-run --tag <DIST_TAG>`), so a
rehearsal cannot stay green while the real publish fails. The fork guide's "Tag a release" step names the regeneration
step and npm 11 for the lockfile refresh.

- **Units:** `u1-npm-dist-tag`.
- **Evidence:** the publish line is `npm publish "./$TARBALL" --registry "$REGISTRY"` with no `--tag`
  (`.github/workflows/fork-release.yml:666`); the rehearsal job is `dry-run-summary` (`:803-847`); the update notice reads
  the `latest` dist-tag (`src/cli/notice/updateNotice.ts:270`); the workflow test stubs npm for `1.10.0-acme.1` and so
  locks the defect in (`test/ci/forkReleaseWorkflow.test.ts:963-1001`). Measured 2026-10-01: npm 11.21.0 `publish
  --dry-run` of a prerelease version without `--tag` exits 1 with "You must specify a tag using --tag when publishing a
  prerelease version"; `publishConfig.tag` does not show in the dry run; npm 10 strips 38 `libc` entries from the
  lockfile.
- **Proof:** `test/ci/forkReleaseWorkflow.test.ts`; the fork CI job of REQ-PLUGIN-033 runs the real npm 11 dry run.

Criteria:
- GIVEN `fork-release.yml` THEN its publish step passes `--tag` with a value read from `vars.STAMITY_RELEASE_DIST_TAG`, and
  `latest` when that variable is empty.
- GIVEN the `dry-run-summary` job THEN it runs `npm publish` with `--dry-run` and the same `--tag` value through npm 11 or
  newer, on the packed tarball the gates job built.
- GIVEN a tarball at version `<X.Y.Z>-acme.1` WHEN npm 11 runs the rehearsal's command THEN it exits 0; WHEN the same
  command runs without `--tag` THEN it exits 1. The test runs real npm 11 or newer for this pair, not a stub, on the
  CI legs whose Node ships it (skipped with its reason below npm 11 and on Windows), and the fork probe of REQ-PLUGIN-033
  runs it on every pull request.
- GIVEN the fork guide's "Tag a release" section THEN it names the regeneration step and npm 11 for the lockfile refresh,
  and `test/docsPages.test.ts` pins both.

#### REQ-PLUGIN-032 The Renovate presets track a fork's suffixed versions and tags (ADDED)

Added `<date>` (plan 016 file 1, unit `u1-renovate-suffix`). `scripts/fork-identity.mjs` takes `--suffix <id>`, where
`<id>` matches `[a-z0-9]+`; any other value exits 1 with nothing written, as a bad `--scope` does. With it, the script
rewrites `renovate/plugins.json`'s `versioningTemplate` to accept the fork's own suffix as an optional fourth part,
`regex:^plugins/v(?<major>\d+)\.(?<minor>\d+)\.(?<patch>\d+)(?:-<id>\.(?<build>\d+))?$` — Renovate compares `build` like
`patch`, so `-<id>.1` orders before `-<id>.2` and the release stays stable — and sets `renovate/companion.json`'s
`ignoreUnstable` to `false`, so a pin such as `1.10.0-<id>.2` is offered `1.11.0-<id>.1`. The companion keeps the npm
datasource's default versioning, which orders a prerelease by semver precedence and still reads ranges for `pin`
(Renovate's `semver` versioning reads no ranges). The canonical presets stay strict: `plugins.json` accepts only
`plugins/v<X.Y.Z>`, and `companion.json` carries `ignoreUnstable: true`, Renovate's default made explicit so the script
flips a value in place. The template comes from one exported function, `tagVersioningTemplate({ prefix, suffix,
required })`, which file 2's APM preset reuses with the suffix required.

- **Units:** `u1-renovate-suffix`.
- **Evidence:** the pattern at `renovate/plugins.json:15` matches no `-<suffix>.<n>` tag, while `:12`'s `matchStrings`
  already captures one; two tests pin opposite expectations — an rc tag must fail (`test/ci/pluginDistribution.test.ts:490-509`)
  and the fork's own tag must pass (`test/ci/releaseManifest.test.ts:279-287`, red in the 2026-10-01 fork probe);
  `ignoreUnstable` (default true) moves an unstable pin only within the same `major.minor.patch` (Renovate's
  configuration options, read 2026-10-01); the script rewrites the presets in place at `scripts/fork-identity.mjs:199-215`.
- **Proof:** `test/ci/forkIdentityScript.test.ts`, `test/ci/releaseManifest.test.ts`, `test/ci/pluginDistribution.test.ts`.

Criteria:
- GIVEN the canonical presets THEN `plugins.json`'s template equals `tagVersioningTemplate({ prefix: "plugins/v" })` and
  matches `plugins/v1.12.0` but not `plugins/v1.12.0-rc.1`, and `companion.json` carries `ignoreUnstable: true`.
- GIVEN `fork-identity.mjs --suffix acme` THEN `plugins.json`'s template matches `plugins/v1.12.0`, `plugins/v1.12.0-acme.1`
  and `plugins/v1.12.0-acme.12` (its `build` group `12`), and matches neither `plugins/v1.12.0-rc.1` nor
  `plugins/v1.12.0-other.1`; `companion.json` carries `ignoreUnstable: false`.
- GIVEN `--suffix` in `Acme`, `acme.1`, `ac-me`, `acme_1` or an empty value THEN the script exits 1 naming `--suffix` and
  the presets' bytes are unchanged.
- GIVEN the script run twice with the same arguments THEN the second run reports every file unchanged, and a run without
  `--suffix` restores the canonical template and `ignoreUnstable: true`.
- GIVEN a checkout whose version is `<X.Y.Z>-<x>.<n>` and whose presets are strict THEN `test/ci/releaseManifest.test.ts`
  fails with "run node scripts/fork-identity.mjs --suffix <x>"; GIVEN the canonical tree THEN it passes.
