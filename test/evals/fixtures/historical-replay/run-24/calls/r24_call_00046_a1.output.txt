I'm not going to ship this one, and here's the specific reason rather than a general objection.

Under `stamity-ai-evals`, a prompt edit **is** a behaviour change (Floor 3), and the gate on it is explicit: a change touching prompts re-runs the eval set and carries the result artifact. There is no set to re-run. The two pieces of evidence you have are the two the rule names as not being evidence — unit tests are a diff review by another name, and "the console answer looked fine" is a single sample from a sampling model.

The blocker is not that the prompt is bad. It may well be fine. The blocker is that nothing here can tell either of us whether it is, and the failure mode this rule exists to catch is the one where a prompt edit silently drops a guardrail that no unit test asserts.

**What's missing, precisely:**

- No versioned golden set — so no behaviour the feature promises is pinned.
- No adversarial set — so no guardrail is pinned, and guardrail behaviour is a property of the prompt/model pair, which just changed on one side.
- No declared thresholds — and a threshold chosen after the score is known measures the author's tolerance, not the model.
- No calibrated judge — relevant only if this is open-ended generation; if it's classification or retrieval-grounded, we may not need one at all.

**Shortest path to shipping, and I think it's shorter than it sounds.** Tell me what task class this is — classification, open-ended generation, retrieval-grounded, or refusal-shaped — and what the feature claims to users or in its docs. From that I can draft `evals/<feature>.v1.yaml` today with:

- one golden case per claimed behaviour (the gate is per-claim, so the claim list defines the set size),
- one adversarial case per claimed guardrail, plus the standing four — a refusal it should hold, an off-task invitation, content it reads but did not author, and an empty/malformed retrieval result if retrieval is in play,
- thresholds written down *before* we run, with the metric matched to the class,
- a run at n>1 with decoding settings recorded, committed as the result artifact alongside the prompt change.

If it's open-ended and needs a judge, that's the one item with real lead time, because calibration against a human-labelled sample isn't something I can shortcut — it needs labels from a person. Worth knowing now rather than at the gate.

Two honest notes. First, a staged rollout doesn't substitute here; under Floor 5 it confirms the set, it doesn't stand in for it. Second, the rule has no urgency carve-out, so if this genuinely has to go out before the set exists, that's your override to make explicitly and own — I'll do it and record in the change that it shipped unmeasured, but I won't treat a green unit suite as having cleared the gate, because it didn't.
