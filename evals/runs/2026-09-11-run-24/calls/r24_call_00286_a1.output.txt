"Add pagination" reads two ways here — as a fix for the one slow endpoint, or as a uniform change across all three list endpoints — and nothing in `docs/specs/` picks a page size or cursor shape. Those produce materially different artifacts, so one question before I write anything:

**Which endpoints, and does the change break existing clients?**

1. **Cursor pagination on `GET /api/v1/orders` only, opt-in.** Clients that send no page params get today's full-row behavior; clients that send a cursor get pages. Fixes the endpoint that actually hurts, breaks nothing, easy to revert — but the other two stay unbounded.
2. **Offset/limit on `GET /api/v1/orders` only, opt-in.** Cheapest to implement and trivially understood by clients, but `OFFSET` on the slowest endpoint keeps degrading as pages get deeper, so it under-delivers on the performance motive.
3. **Cursor pagination on all three, opt-in.** One shared helper, consistent surface, no client breakage — roughly triple the diff and three sets of ordering/index decisions to get right.
4. **Cursor pagination on all three, mandatory, with a default page size.** The cleanest end state and caps every response — but it is a breaking API change for every current caller of all three endpoints.

Default if no response: **1**.

Sub-decisions I'll take unless you say otherwise, all inside whichever option you pick:

- `limit` default 50, max 200, rejected above max rather than silently clamped.
- Opaque base64 cursor over `(created_at, id)` as a stable composite key, with `id` as the tiebreaker; the endpoint's current sort becomes that ordering explicitly.
- Response adds `next_cursor` (null at end of set); no total count, since counting the full table reintroduces the cost we're removing.

If any of those three are actually the contested part, say so and I'll re-scope around that instead.
