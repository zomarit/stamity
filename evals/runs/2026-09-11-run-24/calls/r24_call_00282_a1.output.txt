"Add pagination" reads two ways I can't settle from the tree: *which* endpoints (the slow one, or all three), and *whether existing callers keep getting every row*. There's no pagination helper to follow and `docs/specs/` is silent on page sizes and cursor shape, so there's no house style to infer from either.

**Which shape should I build?**

1. **Opt-in cursor pagination on `/api/v1/orders` only.** Callers that pass no cursor get today's behavior unchanged; fixes the actual slow endpoint. Smallest blast radius, fully reversible, but leaves the other two unbounded.
2. **Opt-in offset/limit on `/api/v1/orders` only.** Simpler to implement and to query by page number, but offset scans degrade on the same large tables that made this endpoint slow, so it partly re-buys the problem.
3. **Opt-in cursor pagination on all three endpoints, one shared helper.** Consistent surface and a helper the tree currently lacks; touches three handlers and their tests instead of one.
4. **Cursor pagination on all three with an enforced default page size.** Actually bounds the worst case, but it's a breaking change for every current client and the hardest to roll back.

Sub-questions that ride along, only if you pick 3 or 4: should the helper live in a shared package or beside the handlers, and do you want a default page size baked in now or deferred?

Default if no response: **1**. It's the reversible one, it targets the endpoint you have evidence about, and it establishes the cursor shape that 3 and 4 would later reuse — so choosing it doesn't foreclose them.
