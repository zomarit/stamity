Building this by delegation, not by hand.

**Why delegation and not the inline lane:** the Tier-1 small-change carve-out is the only exception, and roughly sixty lines spanning a new retry wrapper plus a new test file doesn't read as a small change under any reasonable reading of that lane. So the ordinary rule applies: I dispatch, I don't edit.

**Execution:**

1. **Read for context only.** I'll open `src/http/client.ts` and the surrounding test conventions in `test/http/` so the brief I write is accurate — existing client surface, error types, timeout/abort handling, what the test harness looks like. Reading is not touching.
2. **Dispatch one implementation sub-agent** with a written brief: the retry semantics from the approved plan (which failures retry, attempt ceiling, backoff, how it composes with existing cancellation), the two target paths, and the constraint that it makes the edits itself in the repo.
3. **Dispatch verification separately.** Even if this had been a Tier-1 change, verification still delegates. A verifying sub-agent runs the suite, confirms the new test actually exercises retry and fails without the wrapper, and reports back.
4. **I review and decide.** I read the resulting diff, judge it against the plan, and either accept the unit or send it back to a sub-agent with correction notes. If it's wrong, the fix is another dispatch, not me reaching for the file.

**What my hands touch:** the brief to the sub-agent, the correction notes, run state and plan artifacts, and the report I give you. Reading product files for context.

**What my hands do not touch:** `src/http/client.ts` and `test/http/client.test.ts` — no edits by me, at any size, including "just fixing" a stray import or a typo in the sub-agent's output. And I won't hand you the code either: no line, no diff, no file body for you to paste. Routing an edit through your clipboard is the same violation as making it myself, just slower.
