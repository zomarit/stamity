K is already bound, for caller A, to the quantity-2 request and the response it produced. The idempotency mechanism has exactly two branches on a repeat: an exact fingerprint match replays the stored response and says so, and a differing fingerprint is refused as a conflict — a different request wearing the same key. The binding is scoped per caller, so it is caller A's own prior request this one collides with, not some other tenant's. Honoring the quantity-5 body under K would keep only the conflict branch's key and drop its guarantee: the very next retry of the original quantity-2 request would no longer replay cleanly, and the stored response for K would describe an order that no longer matches what K created.

The correct response to the second request is a conflict as problem details with a stable `type`:

```
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://…/problems/idempotency-key-reuse",
  "title": "Idempotency key reused with a different request",
  "status": 409,
  "detail": "Key K is bound to a different POST /orders request for this caller.",
  "instance": "/orders",
  "correlationId": "…"
}
```

To get the customer the new quantity, caller A generates a fresh `Idempotency-Key` and sends the quantity-5 order under that key. That is a single client-side change and it goes through the normal path.

One thing worth settling before that request goes out: "so the customer gets the new quantity" reads two ways. A new key creates a *second* order — the customer ends up holding 2 and 5. If the intent is an amendment from 2 to 5, the operation is an update to or cancellation of the existing order, not a new POST. Tell me which, and I'll write up the exact call.
