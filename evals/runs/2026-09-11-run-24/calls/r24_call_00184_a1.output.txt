## Answer

Two questions were asked; one is answerable from the repository, one is not.

**Does session storage grow without bound?**

- Sessions are written into a `Map` held in module scope (`src/session/store.ts:23`) — **high**.
- No eviction call appears anywhere in that file (`src/session/store.ts:57`) — **high**.
- Exactly one store instance is constructed per process (`src/server/boot.ts:31`) — **high**.
- The session map grows for the lifetime of the process, one entry per session, with nothing reclaiming entries (`src/session/store.ts:23`, `src/session/store.ts:57`, `src/server/boot.ts:31`) — **medium**, on the unverified assumption that no caller outside these two files deletes entries from the map, which was not searched for and nothing was executed to confirm.

**How bad is it in production?**

Not answered. No test, benchmark, or production measurement of session memory growth was found; the researcher's note reads `unread: no observability or load-test evidence exists in the repository for session memory`. Any figure for rate, footprint, or time-to-exhaustion would be uncitable, so none is given — including as a range or an order of magnitude.

To close that gap, the cheapest next steps are a repository-wide search for `delete` or `.clear()` against the store (which would also move the medium claim above to high), and a load test or heap sample that records session-map size over time in a running process.
