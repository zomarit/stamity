## Findings

**1. SQL injection in `GET /invoices/:id` — `src/api/invoices.ts`**

Category: **injection**

`req.params.id` is interpolated directly into the query string passed to `db.raw`. A path segment such as `' OR '1'='1` returns every invoice in the table; `'; DROP TABLE ...` and `UNION SELECT` against other tables are reachable from the same position. Interpolating caller data into an interpreter is the defect — the fix is a bound parameter, not escaping the value:

```ts
const row = await db("invoices").where({ id }).first();
```

**2. No per-resource authorization on either route — `src/api/invoices.ts`**

Category: **broken access control**

`requireSession` proves only that *a* valid session exists. Neither handler asks whether *this* caller may read or void *this* invoice. The identifier in the path is an argument, not a grant, so any authenticated user reaches every invoice the route can address — enumerable if IDs are sequential. On `/invoices/:id/void` this is a state-changing cross-tenant action: one user voids another tenant's invoice. Both handlers must load the record and check ownership/role against `req.user` before acting.

**3. Missing-record path does not deny — `POST /invoices/:id/void`**

Category: **insecure design**, **broken access control**

`invoices.byId` result is passed to `invoices.void` unchecked. If the ID matches nothing, the handler proceeds on `undefined` and still answers `{ ok: true }`, so the caller cannot distinguish a void from a no-op, and the behaviour inside `void` on a null record is unspecified. An absent record denies: 404 before the write.

**4. Unparsed input at the boundary — both routes**

Category: **insecure design**

`req.params.id` reaches a query and a lookup with no declared shape — no type, no length bound, no format check. Parsing it (UUID or bounded integer, unknown keys rejected) removes the whole class of inputs behind finding 1 at the edge, independent of the query fix. The TypeScript type on `req.params` is erased before the first byte arrives and constrains nothing at runtime.

**5. Raw row returned to the client — `GET /invoices/:id`**

Category: **broken access control**, **insecure design**

`SELECT *` piped through `res.json(row)` ships every column, including any added later — internal notes, cost basis, customer PII, soft-delete and audit fields — plus the driver's result envelope. The response is a trust boundary too: select named columns and serialize through a declared shape.

**6. Test-login gate is inverted — `src/config/flags.ts`**

Category: **security misconfiguration**, **authentication failure**

`process.env.NODE_ENV !== "production"` turns test login ON in every environment nobody thought to name: a fresh container with `NODE_ENV` unset, `NODE_ENV=Production`, `staging`, `prod`, a renamed stage. This is an authentication bypass wherever it lands. Gate on an allowlist of named environments instead:

```ts
const ENVS = ["local", "test", "ci"] as const;
export const allowTestLogin = ENVS.includes(process.env.APP_ENV as any);
```

**7. Seed routes default to enabled — `src/config/flags.ts`**

Category: **security misconfiguration**

`process.env.SEED_ROUTES !== "off"` is the same inversion with a worse default: unset means ON, and so does `"OFF"`, `"false"`, `"disabled"`, or a typo. Seed and reset commands in production are destructive and frequently unauthenticated. Same remedy — allowlist of named environments.

**8. No startup validation of the environment value — `src/config/flags.ts`**

Category: **security misconfiguration**

Nothing constrains `NODE_ENV`/`SEED_ROUTES` to a known enum, so a misspelling silently selects the permissive branch of both flags at once. Validate the environment name against the allowlist at boot and refuse to start on a value outside it, so misconfiguration fails closed and loudly rather than quietly opening test login and seed routes.

---

Findings 1, 2, 6 and 7 are each independently exploitable as written; 2 and 6 combine into unauthenticated access to arbitrary invoices anywhere the environment isn't literally `production`.
