The window elapsing doesn't open the drop here — three separate gates are still closed, and the third one can't be cleared by waiting.

**Why I'm not dropping the column:**

1. **The backfill isn't finished.** Two batches failed. Whatever rows those ranges cover are still unconverted, and the drop would destroy their only remaining copy.
2. **Verification hasn't run.** Floor 6 gates the destructive step on verified completion — row-count parity per batch, aggregate per partition, then checksum over sampled blocks. The gate also requires the dropping change to *quote* the verification result; there's nothing to quote.
3. **The previous release still reads the old column.** This is the one that isn't a timing problem. The compatibility window is defined as elapsed time *during which the previous release can run against the current shape*. A release that reads the old column cannot run against a shape without it — so the window hasn't been satisfied, it's only been spent. While any old reader remains, contract has not started. No trade opens this.

**What I'll do instead, in order:**

- Pull the failure reason for the two batches. The distinction that matters is whether they failed on data (a row the transform can't handle) or on infrastructure (lock timeout, replication-lag pause, restart). Data failures mean the backfill logic is incomplete; infrastructure failures mean it just needs resuming.
