**Question — pagination scope and mechanism (one question, three parts):**

`Add pagination` reads at least two ways here, and they produce different artifacts. The repo has three list endpoints returning every row; only `GET /api/v1/orders` is the slow one. There's no pagination helper in the tree and `docs/specs/` is silent on page sizes and cursor shape, so whatever I write becomes the de facto spec.

1. **Offset/limit on `/api/v1/orders` only.** Additive `?limit=&offset=` query params; absent params preserve today's behavior, so no client breaks. Smallest change, fully reversible. Doesn't touch the other two endpoints, and offset degrades on deep pages — which is exactly where the slow endpoint hurts.
2. **Offset/limit on all three endpoints, plus a shared helper.** Uniform interface across the service and one place to change later. Touches three handlers and three response paths, so triple the review surface and triple the regression risk for two endpoints nobody has complained about.
3. **Cursor-based on `/api/v1/orders`, helper built for reuse.** Actually fixes deep-page cost on the endpoint that's slow. But it invents a cursor encoding that no spec defines, and once clients start round-tripping opaque cursors the shape is effectively frozen — the expensive one to get wrong.

Bundled sub-questions, answer inline if you have opinions; otherwise I'll take the stated fallbacks:

- **Default page size** — fallback `50`, with `limit` capped at `200`.
- **Response shape** — fallback is to leave the existing top-level array untouched and return paging state in headers (`X-Total-Count`, `Link`). Wrapping the body in `{data, next}` is cleaner but breaks every current caller, so I won't do it unless you say so.
- **Spec note** — fallback is to add a short `docs/specs/pagination.md` recording whatever we land on, since the gap is why this question exists.

**Default if no response: 1.** It's the lowest-blast-radius reversible option and it can be upgraded to 3 later without breaking callers, whereas shipping 3 first commits us to a cursor format before anyone has picked one. Note that 1 does not make `/api/v1/orders` fast at depth — it only bounds the default response. If the actual goal is the latency rather than the unbounded payload, say so and I'll go with 3.
