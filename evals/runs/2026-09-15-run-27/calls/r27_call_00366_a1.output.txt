## Findings

**1. SQL injection in `GET /invoices/:id`**
Category: injection

`req.params.id` is interpolated into the query string, so a caller controls SQL syntax, not just a value. `'` terminates the literal and everything after it is parsed as query text — union-select against any table the DB user can reach, or a stacked statement if the driver permits. Fix: bound parameter (`db.raw("... WHERE id = ?", [id])` or the query builder), plus parsing `id` into its declared shape (UUID/integer, bounded length) before it reaches the DB layer at all.

Secondary in the same handler: `SELECT *` piped straight into `res.json` ships every column — internal notes, ledger keys, soft-delete and audit fields — to the client. Respond with an allowlist of fields.

**2. No per-resource authorization on `GET /invoices/:id`**
Category: broken access control

`requireSession` establishes *who* the caller is and nothing more. The handler never asks whether `req.user` may read this invoice, so the identifier in the path acts as a grant: any authenticated user enumerates every invoice in the table. Fix: load the record, then check the caller's relationship to it (org/tenant/owner) and deny otherwise — not a `WHERE id = ?` alone but `WHERE id = ? AND org_id = ?`, or an explicit check after load.

**3. No per-resource authorization on `POST /invoices/:id/void` — and it fails open on a missing record**
Category: broken access control, insecure design

Same missing check, on a state-changing, money-relevant, hard-to-reverse operation: any session voids any invoice by guessing or scraping an ID. Worse than the read case because the damage persists.

Separately, `invoices.byId` has no null handling. If it returns `undefined`/`null` for an unknown ID, `invoices.void(undefined)` is called anyway; if it throws, the throw escapes into whatever the framework's default handler does. Absence must deny — 404/403 before any mutation — and the authorization check must be inside the failure path, not after it.

**4. Test-login flag is on everywhere that isn't literally named `production`**
Category: security misconfiguration, authentication failure

`process.env.NODE_ENV !== "production"` is the inverted form. It turns test login **on** in every environment nobody thought to name: a container started with `NODE_ENV` unset, a stage renamed to `prod`, `Production` with a capital P, a typo in a deploy template. A path that mints sessions without credentials is then reachable in a production-data environment. Fix: allowlist the environments where it is permitted (`["development", "test"].includes(env)`), parse `env` through a closed enum at startup, and refuse to boot on a value outside it.

**5. Seed routes default to enabled**
Category: security misconfiguration, integrity failure

`process.env.SEED_ROUTES !== "off"` is the same inversion with a worse default: unset means on, and only the exact string `"off"` disables it. Any deploy that forgets the variable — or sets `false`, `0`, `disabled` — exposes seed/reset endpoints that overwrite or truncate real data. Fix: same allowlist-of-named-environments gate, defaulting closed, with the value parsed rather than string-compared.

## Priority

Findings 1, 3, and 4 are the ones that shouldn't survive this review: remote SQL execution, unauthenticated-in-effect voiding of arbitrary invoices, and a credential-free login path that is on by default outside one exact string. Findings 2 and 5 are the same two root causes (no per-resource check; inverted environment gate) in their second instance — fixing them in isolation leaves the pattern in the codebase, so it's worth grepping for other `requireSession`-only handlers and other `!== "production"` flags before closing this out.
