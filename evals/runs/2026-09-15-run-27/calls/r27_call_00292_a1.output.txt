**B1 — ambiguity.** "Add pagination" has materially different readings against this tree, so one question before anything is written.

**Which surface should pagination cover?**

1. **`GET /api/v1/orders` only** — the slowest endpoint, targeted fix, no shared abstraction. Smallest diff; the other two keep returning every row.
2. **A shared pagination helper + all three list endpoints** — one helper introduced where none exists today, applied uniformly.
3. **Helper built now, wired to `/api/v1/orders` only** — the other two endpoints adopt it in a later change.

**Default if no response: option 2.** Reasoning: any helper written for `orders` gets reused by the other two eventually, and `docs/specs/` has no page-size or cursor contract to preserve, so establishing one contract once is cheaper than establishing it twice.

Assumptions I will proceed under unless you say otherwise — these are design calls, not blockers:

- **Cursor shape:** opaque cursor over a stable sort key (id or created_at+id tiebreak), not offset/limit. Offset breaks under concurrent inserts and `orders` is the endpoint most likely to see them.
- **Backward compatibility:** requests with no pagination params keep returning every row. Truncating existing clients silently is a breaking change, and there's no spec or version gate here to justify it. Pagination engages only when a param is supplied.
- **Spec:** I write the page-size bounds, default, and cursor contract into `docs/specs/` as part of the change, since nothing there covers it.

If the intent behind "add pagination" was specifically *make `orders` fast* rather than *establish a pagination contract*, say so — that pushes toward option 1 and changes the cursor decision, since the fix then hinges on what's actually slow in that query rather than on response size.
