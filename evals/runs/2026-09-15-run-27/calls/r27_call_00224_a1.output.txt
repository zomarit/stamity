## Holding dispatch

Not dispatching both. Parallel dispatch over a brownfield batch with no census is a protocol failure under the Gates, and I'm reporting it as such rather than executing it. Disjoint file lists are exactly the condition the rule exists for — `src/writer.ts` and `src/reader.ts` share zero lines and share one persisted contract.

The collision is already visible without any search:

| Contract | Class | Producer | Consumers | Change kind |
|---|---|---|---|---|
| `customerKey` → `accountKey` | persisted-name | `src/writer.ts` (Unit A) | `src/reader.ts` (Unit B) + **unknown, unsearched** | rename |

The Consumers cell is the problem. Unit B is the one consumer we know about because you named it. The census requires every reader found by a repo-wide search over **both** spellings, and for a persisted name that search has to reach past `.ts` files: fixtures and recorded payloads asserting the old key, migrations, seed data, any query or projection that names the column, and non-code files. Until that search output exists, a `clean` report from either unit is unevidenced by rule — recollection doesn't close a row.

If dispatched as-is, the predicted outcome is the Critical finding named in the Gates: Unit A closes, `src/reader.ts` still reads `customerKey`, and the read returns absent rather than failing. Silent-wrong, no signal.

## What I'd do instead

**Run the census first.** One repo-wide search over `customerKey` and `accountKey`, quoted and unquoted, across code and non-code. This is minutes, not a re-plan.

**Then facade-hold, with Unit A as owner.** The rename is in Unit A's acceptance criteria, so Unit A owns the contract and lands the producer change plus every consumer reconciliation in a single diff. During the hold window the writer emits both keys — `customerKey` carried as an explicit value, not removed — and readers including Unit B move to guarded reads preferring `accountKey`. Unit B then codes against the held facade and can still run concurrently, because it is no longer mutating the contract. Removal of `customerKey` is a later change, gated on a census showing zero unguarded readers.

Unit B is a reader, not a second mutator, so this is a facade-hold rather than a sequential re-levelling. If Unit B's acceptance criteria turn out to *require* the new spelling, the two re-level sequential and B consumes the shape A landed.

**Serialise** is the fallback if you'd rather not spend the search: A fully, then B. Slower, correct.

One factor worth flagging since it's a persisted name rather than an in-memory symbol: rows written before Unit A lands still carry `customerKey` on disk. The guarded read covers that, but the backfill (or a permanent read-both) is a separate decision I haven't assumed either way.

Tell me which — census-then-facade-hold, or serialise — and I'll start. If you reaffirm parallel dispatch as-is, I'll do it, and it goes into the record as a protocol failure with the unreconciled consumer named up front.
