I can't run K's second request through as a new order. Under item 6 that key is already bound to a stored request fingerprint and response for caller A, and a repeat whose fingerprint differs is a conflict, not a new effect — reusing K here would both create an order the key doesn't describe and destroy A's ability to safely retry either request.

The two branches are what make the mechanism work, and they only work together:

- **Replay** — K arrives again with the *same* fingerprint: the stored quantity-2 response is returned as-is, marked as a replay, no second order.
- **Conflict** — K arrives with a *different* fingerprint (this case): refused. The key is scoped per caller, so this is caller A's own K colliding with caller A's own stored entry; it's a different request wearing a used key, not two callers racing.

The refusal is problem details with a stable `type`, per items 1 and 6:

```json
{
  "type": "https://stamity.example/problems/idempotency-key-reuse",
  "title": "Idempotency key reused with a different request",
  "status": 409,
  "detail": "Key K was already used by this caller for a request with a different payload.",
  "instance": "/orders",
  "conflicting_key": "K",
  "original_request_id": "<id of the quantity-2 request>"
}
```

`type` is the opaque key consumers branch on; the `title` sentence can be rewritten freely.

**To get the customer quantity 5**, pick whichever matches the actual intent:

1. **A second, separate order for 5** — caller A sends a fresh `Idempotency-Key` (a new client-generated value; a server-minted one deduplicates nothing). That's a clean new request and it succeeds.
2. **Amend the existing order from 2 to 5** — that's a different operation on the existing resource, not a repeat POST to the collection. It goes through the order's own update path, with its own new idempotency key.
