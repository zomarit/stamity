Key K is already bound, for caller A, to a request fingerprint of quantity 2 and to the response that request produced. A second request carrying K with quantity 5 has a different fingerprint, so it is refused as a conflict — it is a different request wearing the same key. I'm not going to write it through as a new order.

The mechanism has two branches and the conflict only makes sense next to the other one:

- **Exact repeat** (same caller, same fingerprint): the stored response is replayed and the response says it was a replay. That is what makes a client retry safe.
- **Differing fingerprint under the same key**: conflict, because replaying would return a quantity-2 order for a quantity-5 request, and executing would create a second effect under a key whose whole job is to guarantee one.

Both branches are scoped **per caller**, not globally — caller B may use the string `K` freely without touching caller A's record. Without that scope, unrelated consumers collide on common key values; without the replay branch, the conflict branch would just be an error with no safe path behind it.

The response for this request, per the Floor item 1 and 6:

```
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://example.com/problems/idempotency-key-reuse",
  "title": "Idempotency key reused with a different request",
  "status": 409,
  "detail": "Idempotency-Key 'K' was already used by this caller for a different POST /orders request. Send a new key to place a different order.",
  "instance": "/orders",
  "originalRequestId": "<id of the stored quantity-2 request>"
}
```

`type` is the stable opaque key consumers branch on; the `title` sentence is for humans and can be reworded later without notice.

To get the customer the quantity they now want, one of these — all of which caller A drives:

1. **New order, new key.** Caller A sends POST /orders with quantity 5 and a *fresh* client-generated key. That is the correct move if the customer genuinely wants a second order. Note this leaves both orders standing — quantity 2 and quantity 5.
2. **Amend the existing order.** If the intent was "the first order should have been 5, not 2," this is an update to the order created by K, not a new create. It goes through whatever amend operation the surface exposes, with its own fresh idempotency key.
3. **Cancel and re-place.** Cancel the quantity-2 order, then create quantity 5 under a fresh key.

Which of those is right depends on whether the customer wants 5 total or 7 total — that's a question about the order, and I can't tell from the request. If you tell me which, I can spell out the exact call. I also have no write tool available here, so any of these has to be issued by caller A or by someone with write access regardless.

One thing worth flagging: if caller A's client is reusing a key across requests whose content changed, that is a client-side bug — keys are meant to be minted per logical operation and held constant only across retries of *that* operation. It will keep producing these conflicts until fixed.
