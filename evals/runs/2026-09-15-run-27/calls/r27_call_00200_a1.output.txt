**Why retries hammer the upstream**

The backoff is nominally exponential but the multiplier is set to `1.0` (`src/http/retry.ts:41`). Multiplying the interval by 1 on each attempt leaves it unchanged, so what should be a growing delay is a fixed one — the retry loop fires at a constant interval and the upstream sees evenly spaced repeat traffic rather than a receding one.

The multiplier is read once at construction (`src/http/retry.ts:12-18`), so the value is fixed for the lifetime of the retry instance. There is no per-attempt recomputation that could compensate, and no runtime override path that would let a caller get real backoff from this object.

**Why the tests did not catch it**

`test/http/retry.test.ts:88` asserts that three attempts occur, and asserts nothing about the interval between them. The suite is a count check, not a timing check, so `1.0` and `2.0` are indistinguishable to it. Whatever change lands on the multiplier will pass this suite unchanged — the test gives no signal either way, which is worth knowing before treating a green run as confirmation.

**What the fix touches**

Changing the multiplier to `2.0` is confined to the constant at line 41, given that the loop already applies the multiplier per attempt and only the value is wrong. Two things a work session should decide alongside it:

- **A cap.** With a real multiplier, intervals grow without bound across attempts. At three attempts the ceiling is low, but if the attempt count is ever configurable, an unbounded doubling becomes a long tail of waiting.
- **Jitter.** Deterministic doubling keeps concurrent clients synchronized — they all back off together and retry together. If the hammering seen in production comes from many clients rather than one, backoff alone will thin the traffic without desynchronizing it.

Neither is required to make the multiplier correct, and both are judgment calls about the retry policy rather than facts readable from the source.
