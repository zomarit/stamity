Holding before writing anything — "Add pagination" has two materially different readings here, so per B1 I'm asking once.

**The ambiguity:** three endpoints return every row, but only `GET /api/v1/orders` is a performance problem. "Add pagination" could mean fix the slow endpoint, or establish pagination as a service-wide convention across all three. Those produce different work: the first is a targeted change, the second is a shared helper plus a spec entry plus two more call-site migrations, and it changes the response shape of two endpoints that currently have no complaint against them.

**Question — which scope?**

1. **`/api/v1/orders` only.** Keyset/cursor pagination on the slow endpoint. No shared helper, no changes to the other two. Smallest diff, fixes the actual pain.
2. **All three, one helper.** Build a pagination helper in the tree, apply to all three list endpoints, write the page-size/cursor-shape contract into `docs/specs/`. Breaking response-shape change on two endpoints.
3. **Helper now, `/orders` only as first consumer.** Build the helper and the spec entry, wire only `/orders` to it, leave the other two for a follow-up. Sets the convention without the breaking change today.

**Default if you don't respond:** option 1. It is the reversible one — it doesn't commit the service to a convention I'd be inventing from nothing, and options 2 and 3 stay open afterward.

**Assumptions I'll proceed on either way, unless you say otherwise:**
- Cursor-based, not offset — offset doesn't actually help the slowest endpoint at depth. This requires a stable monotonic sort key on orders; if there isn't one, I'll stop and come back rather than invent an ordering.
- Opaque cursor string, `?limit=&cursor=`, default limit 50, max 200. `docs/specs/` is silent, so these are mine, not the repo's — flagging that so the numbers get reviewed rather than inherited.
- Existing unpaginated callers break the moment the response shape changes. If `/orders` has consumers you care about, tell me and I'll gate it behind a param instead.
