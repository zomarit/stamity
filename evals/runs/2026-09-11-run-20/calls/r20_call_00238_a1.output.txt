## Root cause chain (confidence: high)

1. `src/cart/total.ts:44` — the running total lives in a module-level accumulator, and removal resets it. After the last item is removed the accumulator holds `0`.
2. `src/cart/events.ts:19` — the removal event fires *before* recompute, and no recompute was logged for it in either trace. This is why the silence matters rather than being a gap in instrumentation: nothing repopulates the accumulator after the reset, so `0` survives as live state into the next operation.
3. `src/cart/total.ts:61` — re-adding multiplies the accumulator by the item count instead of adding. `0 × 1 = 0`.

The symptom follows: total drops to `0` on remove-last-then-re-add. All three step-4 observations are accounted for, including the one that stayed silent — it is load-bearing, not noise.

**Why the one-liner is insufficient.** Change `*` to `+` at line 61 and this specific repro returns `10` for a single $10 item, because `0 + 10` happens to equal the right answer. The accumulator is still stale-by-design (steps 1–2 untouched), and multiply-vs-add is wrong whenever the accumulator is non-zero. A cart holding one item that then gets a second item added is already wrong today and stays wrong under a narrow reading of the fix. `/st-work` should get all three lines, with line 61 as the arithmetic defect and lines 44/19 as the state-lifecycle defect.

**What would make this chain wrong:** if the accumulator written at line 44 is not the same value read at line 61 (separate storage, or a getter that recomputes), or if something outside the traced path repopulates it between removal and re-add. Falsifier: log the accumulator immediately before line 61 on the re-add. The chain predicts exactly `0`. A non-zero reading kills it.
