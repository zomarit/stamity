## Findings

### 1. `src/api/invoices.ts` — `GET /invoices/:id`
**Category:** injection, broken access control

Two defects in four lines.

`req.params.id` is interpolated into the SQL string. A path segment of `' OR '1'='1` returns the invoices table; `'; DROP TABLE ...` or a stacked subselect goes further. `db.raw` with bound parameters (`db.raw("SELECT ... WHERE id = ?", [id])`) removes it; the parameter must also be parsed into a declared shape first — id is presumably a UUID or integer, so bound it to that type and reject everything else before the query is built.

`requireSession` attaches `req.user` and stops. Nothing asks whether this caller may read *this* invoice, so any account with a valid cookie enumerates every invoice in the system by walking the id space. The identifier in the path is an argument, not a grant. Load the record, then check it against `req.user` — ownership, org membership, whatever the tenancy model is — and deny when the check does not affirmatively pass.

`SELECT *` then `res.json(row)` ships whatever columns the table happens to have, now and after the next migration, straight to the caller. The response crosses a trust boundary outward: project the named fields the endpoint is specified to return.

### 2. `src/api/invoices.ts` — `POST /invoices/:id/void`
**Category:** broken access control, insecure design

Same missing per-resource check, on a state-changing operation: any authenticated caller voids any invoice belonging to anyone. Voiding is also the kind of action that wants to be authorized against the invoice's *state* as well as its owner — an already-paid or already-voided invoice.

Separately, `invoices.byId` returning `undefined` or `null` for an unknown id flows into `invoices.void(invoice)` unguarded. The behavior then depends on what `void` does with a nullish argument, which is the wrong place for that decision to live. An absent record denies: check the lookup result and return 404/403 before calling `void`.

### 3. `src/config/flags.ts` — `allowTestLogin`
**Category:** security misconfiguration, authentication failure

`process.env.NODE_ENV !== "production"` enables a test-login path in every environment that is not exactly that one string. A fresh container with `NODE_ENV` unset, a stage renamed to `prod`, `Production` with a capital, a CI value nobody enumerated — all get an authentication bypass. Gate on an allowlist instead: `["development", "test"].includes(env)`, with `env` read once through a parser that refuses to boot on any value outside the declared enum.

### 4. `src/config/flags.ts` — `seedRoutesEnabled`
**Category:** security misconfiguration

`process.env.SEED_ROUTES !== "off"` is a one-element denylist and defaults to ON when the variable is absent, which is the state of every environment that has not been explicitly configured — including production on first deploy. `"Off"`, `"false"`, `"0"`, and a typo all enable seed routes. Gate these on the same named-environment allowlist as the test-login path rather than on a string comparison against the disabled value.

### 5. `src/config/flags.ts` — no environment enum at startup
**Category:** security misconfiguration, insecure design

Both flags read `process.env` inline with no validation, so there is no point at which an unrecognized environment value stops the process. Parse the environment into a declared enum at boot and refuse to start on anything outside it; that is what makes the allowlists in findings 3 and 4 hold.

---

**Suggested order of work:** the SQL injection and the two authorization gaps are exploitable by any authenticated user today. The flags are exploitable by anyone who can reach a non-production-named deployment, which may already include production.
