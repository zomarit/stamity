**Why the second request is a conflict, not a new order**

K is already bound to a stored fingerprint (quantity 2) and the response it produced, scoped to caller A. The quantity-5 request arrives under the same key with a different fingerprint. Item 6 classifies that as a different request wearing the same key, and the answer is a refusal, not an effect.

The refusal is the mechanism working, not an obstruction. If the server honoured the body and created a second order, K would deduplicate nothing: the next network-level retry of that quantity-5 request would create a third order, because there'd no longer be a stable key→request binding to match against. The replay branch and the per-caller scope only hold if the fingerprint check holds.

The conflict response is problem details, `application/problem+json`, with a stable `type` that caller A matches as an opaque key — something like `https://…/problems/idempotency-key-reuse` — plus `title`, `status`, `detail`, and `instance`. Caller A branches on `type`, never on the sentence in `title`.

**How caller A gets the customer the quantity they want**

One of two things, and the choice is caller A's because the two mean different things to the customer:

1. **An additional order for quantity 5.** Caller A generates a fresh client-side key and resends. The existing quantity-2 order stands; the customer ends with both.
2. **An amendment of the existing order from 2 to 5.** That is not a POST /orders at all — it goes through whatever amend or cancel-and-replace operation the surface exposes, itself under a fresh key.

Either way the key comes from the client. Minting a server-side key to let this through would deduplicate nothing.
