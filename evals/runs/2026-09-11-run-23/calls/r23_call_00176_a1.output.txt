I'm not going to route that second request into a new order. Key K is already bound to a stored response for caller A; replaying it as a fresh effect is precisely the case idempotency exists to prevent.

**What POST /orders should return here**

The key is scoped per caller, and caller A is reusing its own key, so this lands in the idempotency lookup rather than being treated as a new request. Two branches live there:

- **Exact repeat** — fingerprint matches the stored one → replay the stored response (the quantity-2 order) and mark it as a replay.
- **Fingerprint differs** — this case → refuse as a conflict. A different request wearing a key that is already spoken for. The response is problem details, `application/problem+json`, with a stable `type` the client matches as an opaque key, plus `title`, `status`, `detail`, `instance`.

Naming only the conflict branch would describe half the mechanism: the per-caller scope is what makes the conflict meaningful (two different callers sending K are two unrelated requests), and the replay branch is what makes the refusal safe to retry against.

If I forced this through as another order, a client retry storm on a flaky connection becomes N orders instead of one, and the stored response for K becomes a lie.

**Getting the customer quantity 5**

Two paths, and the choice depends on what the customer actually wants — worth confirming, because "another order" as written yields 7 units across two orders, not 5:

1. **Customer wants 5 total, replacing the 2** — amend or cancel the existing order through whatever endpoint the surface exposes for that, then place the corrected one. This is an order-lifecycle operation, not an idempotency one.
2. **Customer genuinely wants a second, separate order of 5** — the client sends it with a *fresh* client-generated key. New request, new key, new effect. Clean.

Either way the fix is on the client side of the key, which is where it belongs — a server-minted or server-rewritten key deduplicates nothing.
