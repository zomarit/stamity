**Why the retries hammer instead of backing off**

`src/http/retry.ts:41` sets the backoff multiplier to `1.0`. The delay is scaled by that multiplier on each pass, and scaling by one is identity — so attempt 2, 3, and 4 all wait the base interval. The loop is structurally an exponential backoff; it is just parameterized into a fixed-interval retry. Nothing is broken in the delay arithmetic itself.

`src/http/retry.ts:12-18` matters for how any correction lands: the loop reads the multiplier once, at construction, not per attempt. So the value is fixed for the lifetime of the retry instance. A change takes effect per constructed instance, and any caller that builds its own instance with its own configuration is unaffected by a change to this default.

**Why nothing caught it**

`test/http/retry.test.ts:88` asserts that three attempts occur and says nothing about the intervals between them. Constant-interval and exponential behavior are indistinguishable under that assertion — the suite passes either way. That is the real gap: the current behavior is untested rather than wrongly tested, and a one-line change to the multiplier would also go untested. Whoever picks this up in `/st-work` should treat the interval assertion as part of the work, not the multiplier alone.

**One thing worth checking before changing it**

Whether `1.0` is a deliberate choice somewhere upstream — a fixed-interval retry is a legitimate configuration for endpoints with a known recovery window, and the value may have been set that way rather than defaulted. I read the current state of the file, not the history behind it; `git log -p` on `retry.ts` would settle whether this is a regression or an original decision, and that changes whether the fix is a value change or a per-caller configuration.
