## Findings

**1. Injection — `src/api/invoices.ts`, `GET /invoices/:id`**

`req.params.id` is interpolated directly into the SQL string passed to `db.raw`. A path segment of `' OR '1'='1` returns the whole invoice table; `'; --` and stacked-statement variants reach further depending on the driver. Bind the parameter (`db.raw("SELECT ... WHERE id = ?", [id])`) or use the query builder. Quoting the interpolation by hand is the pattern that keeps failing — don't.

**2. Broken access control — `src/api/invoices.ts`, both routes**

`requireSession` establishes *who* the caller is and nothing more. Neither handler loads the invoice and asks whether `req.user` may read or void *that record*. The `:id` in the path is an argument, not a grant: any authenticated user can enumerate identifiers and read every invoice in the system, and void every invoice in the system. The void route is the more serious of the two — it is an unauthenticated-in-effect, state-changing, money-affecting mutation.

Both handlers need a server-side per-resource check after loading the row: does this invoice belong to a tenant/account this caller may act on, and is the caller's role permitted this action.

**3. Insecure design — `GET /invoices/:id` response shape**

`SELECT *` is serialized straight into the response body. Whatever columns the table gains later — internal notes, cost basis, customer PII, soft-delete metadata — ship to the caller automatically. The response crosses a trust boundary too; project an explicit allowlist of fields.

**4. Broken access control, insecure design — `POST /invoices/:id/void` on a missing record**

`invoices.byId` result is passed to `invoices.void` with no check. If a nonexistent id yields `undefined` or `null`, the behavior of `void(undefined)` is unspecified by this diff, and "unspecified" is not "denied." Absence must take the deny branch explicitly: 404/403 before any mutation.

**5. Security misconfiguration, authentication failure — `src/config/flags.ts`, `allowTestLogin`**

`process.env.NODE_ENV !== "production"` is the inverted form. A fresh container with `NODE_ENV` unset, a renamed stage, `Production`, `prod`, or a typo all turn the test-login path **on**. This is a full authentication bypass gated on a string nobody validates.

Gate on an allowlist instead — `["development", "test"].includes(env)` — and have startup refuse to boot when `NODE_ENV` is outside the declared enum, so a misspelling is a crash rather than a silent grant.

**6. Security misconfiguration — `src/config/flags.ts`, `seedRoutesEnabled`**

`process.env.SEED_ROUTES !== "off"` is a denylist of one known value, defaulting open. Unset, `"false"`, `"0"`, `"OFF"`, `"disabled"` all enable seed routes in production. Seed and reset commands must be gated on the same named-environment allowlist as the flag above, not on the absence of a magic string.

## Lower confidence — verify against code not in this diff

- **Broken access control (CSRF):** `POST /invoices/:id/void` is a cookie-authenticated state change. If the session cookie is not `SameSite=Lax/Strict` and there is no token or origin check in middleware upstream, a cross-site form post voids invoices. I can't see the cookie or middleware config from this diff.
- **Logging failure:** voiding an invoice is a financial mutation with no audit record in the handler. If the write isn't logged with actor, target, and timestamp elsewhere in `invoices.void`, there's no trail after the fact.

## Priority

Fix 5 and 6 first — they are one-line changes that currently expose authentication bypass and seed routes to production. Then 2 (void route), then 1, then the rest.
