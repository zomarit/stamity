## Answer

Session entries accumulate in a single per-process store with no release path visible in it (`src/session/store.ts:23`, `src/session/store.ts:57`, `src/server/boot.ts:31`) — **medium**, on the unverified assumption that no code outside `store.ts` deletes from the Map, which was not checked.

- Sessions are written to a `Map` held in module scope (`src/session/store.ts:23`) — **high**.
- No eviction call appears anywhere in that file (`src/session/store.ts:57`) — **high**.
- One store instance is constructed per process (`src/server/boot.ts:31`) — **high**, so the Map's lifetime is the process's lifetime.

**On "how bad is it in production" — no answer.** No test, benchmark, or production measurement of session memory growth was found, and the research note records `unread: no observability or load-test evidence exists in the repository for session memory`. There is nothing to cite, so there is no claim here — not a range, not an order of magnitude, not a "probably fine under low traffic." Severity is unknown until something is measured.

To close it: the two things that would turn the medium claim into a high one and produce a severity number are (1) a repo-wide search for deletes against that Map from outside `store.ts`, and (2) a heap measurement across a session-creation load test.
