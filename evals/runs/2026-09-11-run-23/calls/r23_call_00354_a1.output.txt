## Findings

**1. `GET /invoices/:id` — SQL injection**
Category: injection

`req.params.id` is interpolated directly into the query string. `db.raw` receives whatever the caller put in the path segment, so `1' OR '1'='1` returns every invoice and `1'; ...` reaches whatever else the driver permits in a statement. The path parameter is caller data crossing a trust boundary and is never parsed into a declared shape — no type, no length or format bound.

Fix: bound parameters (`db.raw("SELECT ... WHERE id = ?", [id])` or the query builder), and parse `id` into its declared shape first — if invoice IDs are UUIDs, validate as UUID and reject otherwise.

**2. `GET /invoices/:id` — no per-resource authorization**
Category: broken access control

`requireSession` proves only that *a* valid session exists; it never asks whether this caller may read *this* invoice. The route check passes, so it grants every invoice the route can reach. The ID in the path is being treated as a grant rather than an argument.

Fix: load the record and check ownership/tenancy against `req.user` before returning it; deny when the record does not exist or the check throws.

**3. `GET /invoices/:id` — unparsed response shape**
Category: insecure design

`SELECT *` is serialized straight to the client. The response is a trust boundary too: every column the table has now or gains later (internal notes, processor references, ledger fields) ships to the caller with the next migration, silently.

Fix: select an explicit column list, or map the row through a declared response shape.

**4. `POST /invoices/:id/void` — no per-resource authorization, and no closed failure path**
Category: broken access control, insecure design

Same missing check as (2), but on a state-changing action: any authenticated caller can void any invoice by ID. Additionally, `invoices.byId` has no result check — if it returns null/undefined for an unknown ID, `invoices.void(undefined)` is called with an absent record instead of denying. An absent grant must deny.

Fix: load the invoice, 404/403 when absent, check that `req.user` may void *this* invoice, then act. `req.params.id` also needs the same shape validation as (1).

**5. `src/config/flags.ts` — both flags default ON outside the named case**
Category: security misconfiguration, authentication failure

`allowTestLogin = process.env.NODE_ENV !== "production"` is the inverted form. It turns test login ON in every environment nobody thought to name: a fresh container with `NODE_ENV` unset, a stage renamed to `prod`, a `productoin` typo, a container where the var was dropped. Test-login paths are an authentication bypass wherever they are reachable.

`seedRoutesEnabled = process.env.SEED_ROUTES !== "off"` fails open the same way — unset means enabled, and `"false"`, `"0"`, `"OFF"` all mean enabled. Seed/reset routes reachable in production are destructive.

Fix: gate both on an allowlist of named environments (`["local", "test", "ci"].includes(env)`), parse `NODE_ENV` against an enum at startup and refuse to boot on a value outside it, and make the seed flag an explicit opt-in (`SEED_ROUTES === "on"` *and* a permitted environment).

## Summary

| # | Location | Category |
|---|---|---|
| 1 | `GET /invoices/:id` | injection |
| 2 | `GET /invoices/:id` | broken access control |
| 3 | `GET /invoices/:id` | insecure design |
| 4 | `POST /invoices/:id/void` | broken access control, insecure design |
| 5 | `config/flags.ts` | security misconfiguration, authentication failure |

Findings 1, 2, and 4 are blocking on their own. Finding 5 is blocking if either flag gates anything reachable over the network.
