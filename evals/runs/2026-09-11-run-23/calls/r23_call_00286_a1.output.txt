"Add pagination" reads two ways that produce different artifacts, and nothing in the tree decides it for me: there's no pagination helper to copy a convention from, and `docs/specs/` says nothing about page sizes or cursor shape. Two axes are open — which endpoints, and which page mechanism.

**Which of these should I build?**

1. **Offset/limit on `GET /api/v1/orders` only** — smallest diff, no new concepts, fixes the endpoint that's actually slow; deep pages (`offset=50000`) stay slow because the DB still scans past them.
2. **Cursor on `GET /api/v1/orders` only** — constant-time at any depth and stable under concurrent inserts; requires me to invent a sort key and an opaque cursor encoding with no spec to check them against, and cursors are hard to change once clients hold them.
3. **Offset/limit on all three list endpoints** — one consistent convention across the API surface; triples the blast radius and touches two endpoints with no demonstrated performance problem.
4. **Cursor on all three** — the most complete outcome; largest surface area, and it commits every endpoint to an encoding I'd be guessing at.

Two sub-questions folded into the same answer, with the assumptions I'll use if you don't address them:

- **Page size** — I'll use `limit` defaulting to 50, capped at 200.
- **Compatibility** — I'll make the params optional and leave the response as a bare array plus `X-Total-Count` / `X-Next-Cursor` headers, so existing callers that send no params keep today's behavior. Say the word if you'd rather have a wrapped `{data, page}` envelope; that one is a breaking change for every current client.

**Default if no response: 1.** It's the lowest-blast-radius option that still addresses the actual complaint — one endpoint, one additive change, no encoding I can't revise later. Options 2–4 are all reachable from it; going the other direction means unwinding a cursor format clients have already stored.
