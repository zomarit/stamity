I'm not going to run the drop. Two things block it, and the elapsed window doesn't clear either one.

**The previous release still reads the old column.** Dropping it now means that release can no longer run against the current shape — you lose your rollback the moment the statement commits. Per the floor: while any old reader remains, contract has not started. The compatibility window is a *second* condition, not a substitute for the first.

**Verification hasn't run, and the backfill isn't finished.** Two batches failed, so some rows have no new-column value. A drop is gated on verified completion, not elapsed time, and the change that drops has to quote the verification result — there is no result to quote. If those failed ranges are real gaps, the drop destroys the only remaining copy of that data and no reversal exists short of a backup restore, which discards every write since the snapshot.

The sequence to actually get you there:

1. **Resume the two failed batches** from their persisted boundaries and capture why they failed — a transient lock timeout and a data-shape problem (nulls, encoding, an unexpected value) lead to different fixes. If it's the latter, the backfill logic needs a change before rerun.
2. **Run verification, cheapest first** — row-count parity per batch, aggregate check per partition, then a checksum over sampled blocks. Record the output; it goes in the drop's change description.
3. **Confirm no old readers remain.** Old column reads have to leave the previous release, and that release has to be verified runnable against the new shape. If the current deployed-previous release still reads it, the compatibility window restarts from the release that stops reading — the clock that elapsed was measuring against the wrong baseline.
4. **Then the drop ships on its own**, separate from the backfill change, with a lock timeout and statement timeout set.
