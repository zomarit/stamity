"Add pagination" resolves at least two ways here, and they produce different artifacts, so I want one decision from you before writing anything.

What I have: three list endpoints returning every row, `GET /api/v1/orders` the slowest of them; no pagination helper anywhere in the tree; `docs/specs/` silent on page sizes and cursor shape. So both the *scope* (one endpoint or all three) and the *mechanism* (offset or cursor) are unpicked, and the cursor shape would be mine to invent rather than to follow.

**Which of these should I build?**

1. **Offset/limit on `/api/v1/orders` only.** Smallest diff, easiest to revert, leaves the other two endpoints untouched — but deep pages still scan, so the worst-case cost on the slow endpoint is deferred rather than removed.
2. **Cursor pagination on `/api/v1/orders` only.** Actually fixes deep-page cost — but I'd have to pick a stable sort key and invent a cursor encoding with no spec to point at, and that shape is hard to change once clients depend on it.
3. **Shared offset helper applied to all three endpoints.** Consistent surface and one place to swap in cursors later — but it touches every list caller and forces client updates on three surfaces at once.

Two things that apply to all three: any of them changes the response envelope for callers currently receiving a bare array, so tell me if I should add pagination behind an opt-in parameter and keep the unparameterized response as-is. And if you have a page-size ceiling or a cursor format already in mind from outside the repo, say so — otherwise I'll pick defaults and write them into `docs/specs/` as part of the change.

Default if no response: **option 1**, with pagination opt-in via query parameter so existing callers keep their current response. That's the lowest-blast-radius version and the one that doesn't lock in a cursor format I'd be guessing at.
