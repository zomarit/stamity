## Findings

### 1. `src/api/invoices.ts` — `GET /invoices/:id`
**Category: injection; broken access control**

Two independent defects in four lines.

*Injection:* `req.params.id` is interpolated directly into the SQL string passed to `db.raw`. The quoting around `'${...}'` is hand-written escaping of caller data, which is the pattern that keeps failing — `1' OR '1'='1` returns the whole invoice table, and `'; DROP ...` or a `UNION SELECT` reaches anything the connection's role can touch. The path parameter also crosses a trust boundary with no declared shape: nothing asserts it is, say, a UUID or bounded integer.

*Broken access control:* `requireSession` authenticates and stops there. The query filters on `id` alone, never on ownership, so any caller with a valid session reads every invoice in the system. The identifier in the path is being treated as a grant.

Fix: bind the parameter (`db("invoices").where({ id })` or `db.raw("... WHERE id = ?", [id])`), validate `id` into a declared shape before the query, and scope the read to the caller's tenant/account by loading the record and checking it against `req.user`.

### 2. `src/api/invoices.ts` — `POST /invoices/:id/void`
**Category: broken access control**

`invoices.byId(req.params.id)` loads whatever record the path names, and `invoices.void` acts on it. No check asks whether this caller may void this invoice. A session-holder can void any customer's invoice by guessing or enumerating an id — a state-changing, likely irreversible financial operation. The route-level `requireSession` passes, and a check that passes on the route grants every record the route can reach.

Secondary, same route: if `byId` returns `null`/`undefined` for an unknown id, that value is handed to `void` rather than producing a 404. The absent record should deny, not fall through into the mutation.

Fix: after loading, assert the invoice belongs to the caller (and that voiding is permitted in its current state), denying on both missing record and failed check.

### 3. `src/config/flags.ts` — `allowTestLogin`
**Category: security misconfiguration; authentication failure**

`process.env.NODE_ENV !== "production"` is the inverted form. It turns the test-login path ON in every environment nobody thought to name: a fresh container with `NODE_ENV` unset, a renamed stage, `Production`, `prod`, a typo in a deploy manifest. A single misspelled environment variable in a production rollout enables an authentication bypass.

Fix: gate on an allowlist of named environments (`["local", "ci", "dev"].includes(env)`), and validate `NODE_ENV` against an enum at startup, refusing to boot on a value outside it.

### 4. `src/config/flags.ts` — `seedRoutesEnabled`
**Category: security misconfiguration**

`process.env.SEED_ROUTES !== "off"` is a denylist of exactly one string, defaulting to enabled. Unset, misspelled (`"OFF"`, `"false"`, `"0"`), or absent from the production config, seed and reset routes are live — routes that by nature wipe or overwrite data. This is the same inversion as above with an even narrower deny term.

Fix: same allowlist-of-environments gate, defaulting off, with startup validation.

---

The two config flags share one root cause, and fixing them together is one change: a parsed, enum-validated environment value plus an explicit allowlist per capability. Items 1 and 2 also share one: authorization on these routes is currently authentication only, and every route in this file that takes an `:id` should be audited on the same basis, not just the two in this diff.
