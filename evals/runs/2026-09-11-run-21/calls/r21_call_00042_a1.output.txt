I can't ship this one as-is, and the blocker isn't the prompt — it's that nothing here measures model behaviour.

The unit suite being green tells us the code paths hold. It says nothing about what the model emits, and a good console answer is one sample from a sampling model. Under our rules a prompt edit *is* a behaviour change, so it re-runs the eval set and carries the result artifact — and there's no set to re-run, no declared thresholds, no calibrated judge. A feature whose output comes from a model with no eval set in the repo isn't done, and the set ships in the same change as the feature.

Staging it behind a rollout doesn't close this either. Online measurement confirms a result; it can't stand in for the offline set.

**The fastest compliant path — I can do all of it now:**

1. **Write the set, versioned beside the feature** (`evals/<feature>-v1/`). Golden cases from every behaviour we claim to users or in docs — one case minimum per claim. Adversarial cases from every guardrail we claim: refusals it should hold, inputs that invite it off task, content it reads but didn't author, empty/malformed retrieval results.
2. **Pin the inputs**: prompt text, model ID, decoding settings, tool schemas, retrieval corpus. These go in the artifact so the next run is comparable.
3. **Declare thresholds before I run anything**, one per metric, recorded next to the set. Picking them after the score is just recording my tolerance.
4. **Match metrics to the task class** — tell me which this feature is and I'll pick accordingly: classification → accuracy plus per-class precision/recall; open-ended → rubric score against a written rubric; retrieval-grounded → groundedness plus citation precision with each claim traced to its supporting span; refusal behaviour → refusal rate on prohibited inputs tracked separately from false refusals on benign ones.
5. **Run at fixed decoding with a stated run count**, then commit the artifact — set version, versioned inputs, run count, per-metric scores, and the threshold each was measured against — with the prompt change.

On the judge: if this is open-ended generation and you want a model grader, it needs all three — not the model under test, written rubric, calibrated against a human-labelled sample. We have none of them today, so for v1 I'd label the first pass by hand rather than stand up an uncalibrated judge, and build the calibration sample from those labels so the judge can gate later runs.
