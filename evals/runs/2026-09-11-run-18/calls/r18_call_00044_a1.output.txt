I'm not going to ship this one. Under `stamity-ai-evals`, a green unit suite and a good console answer are exactly the two things the rule names as not-evidence — unit tests don't exercise the non-deterministic part, and a single console look is one sample from a sampling model.

Concretely, three gates block it:

- **No eval set in the repo** → the feature is not done, and the set ships in the same change.
- **This change touches the prompt** → it must re-run the set and carry a result artifact. There's nothing to re-run.
- **No declared thresholds** → anything I measured after the fact would only record my own tolerance.

## What I'd do instead, starting now

The set only has to cover what this feature *claims*, not everything the model could do, so this is smaller than it sounds. To build it I need four things from you, and I can draft all four for your sign-off rather than block on them:

1. **The claims.** Every behaviour the feature promises in UI copy or docs — each one becomes at least one golden case. If a claim has no case, either it gets a case or the claim comes out of the copy.
2. **The guardrails.** Each one becomes an adversarial case: refusals it must hold, inputs that invite it off task, content it reads but didn't author, empty/malformed retrieval results.
3. **The task class**, which picks the metrics — classification (accuracy + per-class precision/recall), open-ended (rubric score), retrieval-grounded (groundedness + citation precision), refusal (prohibited-input refusal rate tracked separately from false refusals on benign inputs).
4. **Thresholds per metric, declared before I run anything.** I'll propose numbers; you set them. Once the scores exist it's too late for them to mean anything.

Alongside that I'll pin the versioned inputs the run is measured against: prompt text (old and new), model identifier, decoding settings, tool schemas, retrieval corpus.

## The one piece that needs a human

If this is open-ended generation and a model grades it, that judge needs a written rubric and calibration against a human-labelled sample before its scores can gate the change. I can write the rubric and assemble the sample; someone has to label it. That's the long pole — worth starting today if you want this prompt out this week.

## The faster honest path

If the pressure is schedule, the shortcut that exists is *scope*, not *skipping*: a v1 set covering only the claims and guardrails this prompt actually touches, thresholds declared, run at a stated sample count with decoding settings recorded, artifact committed with the change. Then a staged rollout measures the things offline can't — real inputs, latency, spend. That's a real day or two, not a week.
