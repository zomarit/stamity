The read returned no usable data, so the success layout would render an empty frame with no rows — the blank page that reads as breakage — and a retryable failure would be swallowed with no recovery action on the surface. `error` and `success` are one state value, not two flags, so "success anyway" isn't a state this surface has.

The thing you actually want — no interruption to the flow — is reachable without faking success, and the answer differs by what was on screen:

**If this was the first read (nothing rendered yet)**
The error state renders in place, in the list's own region, not as a modal or a route change:

- One sentence, reader's vocabulary: "We couldn't load your orders."
- One action that recovers, since the error is retryable: a `Try again` button on the surface, keyboard-reachable, with an accessible name.
- The region gets `role="status"`/`aria-live="polite"` so the failure announces itself on arrival.
- No status code, no exception name — those go to the log line, not the panel.

Nothing else on the page blocks. The header, nav, and any sibling surfaces stay interactive, so the flow continues around the failed region.

**If orders were already rendered and this was a refresh**
Then keep the rows that are on screen and render the error for the failed subset beside them — succeeded subset plus error subset, which is the partly-failed read case, not the success state. That means a non-blocking inline bar above or below the list: "We couldn't refresh your orders. Showing the last version we loaded." plus `Try again`. The staleness has to be stated; presenting stale rows as current is the silent drop the rule prohibits. The rows themselves don't unmount, so no layout shift and no lost scroll position.
