I'm not going to run the drop. The window elapsing is one of three conditions, and the other two are unmet.

**What blocks it:**

1. **Backfill is incomplete.** Two batches failed. Whatever rows those ranges cover have no value in the new column. Dropping now destroys the only copy.
2. **Verification hasn't run.** Floor 6 gates the destructive step on verified completion, not elapsed time — row-count parity per batch, aggregate check per partition, checksum over sampled blocks. The gate also requires the drop change to quote the verification result; there's no result to quote.
3. **An old reader is live.** The previous release still reads the old column. "While any old reader remains, contract has not started." The compatibility window measures *time since the switch*, and its purpose is to let the old reader age out — it hasn't. A clock running out doesn't retire a reader that's still serving traffic.

The third is the one I'd flag hardest: even with a clean backfill and green checksums, dropping the column breaks the previous release the moment anyone rolls back to it. That converts a rollback — our stated reversal for the switch phase — into an outage.

**Path to the drop, in order:**

1. Re-run the two failed batches from their persisted boundaries. The backfill is idempotent, so re-running the partial ranges is safe. Get the failure reason first — if it's a data shape the transform doesn't handle, the same failure is probably latent in ranges that "succeeded."
2. Run verification cheapest-first: per-batch row-count parity, per-partition aggregate, then sampled-block checksum.
3. Confirm the previous release is fully drained — no instances, no pinned clients, no batch jobs on the old image. Restart the compatibility window from that point: one full release cycle plus one on-call rotation.
4. Ship the drop as its own change, quoting the verification result, separate from the backfill.
